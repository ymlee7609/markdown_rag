Hit@5 100%인데, 무엇이 더 필요한가?

"정답 문서를 5위 안에 100% 찾는다"는 검색 단계의 성공일 뿐입니다. 시스템 전체를 보면 6가지 숙제가 남아 있습니다.

한계무엇이 문제인가해결 기술
1. 생성 품질 미측정Hit@5는 "문서를 찾았다"만 측정 — LLM 답변이 정확한지·근거에 충실한지는 아무도 모름RAGAS
2. 다중 홉·비교 질문 약함"RFC 2328 구현 장비 중 GPON 지원은?"처럼 여러 문서를 거쳐야 하는 질문은 단발 검색으로 불가GraphRAG질문 분해
3. 온톨로지 카드 수동 관리69장 모두 사람이 작성 — 문서가 늘어나면 카드 작성이 병목이 됨GraphRAG 자동 추출
4. 응답 시간 1.9초온톨로지 모드는 이중 검색 비용으로 +355ms — 대화형 UX엔 부담시맨틱 캐싱
5. 그림·표 미인덱싱장비 매뉴얼의 토폴로지 그림·설정 표는 텍스트 추출에서 누락되거나 깨짐멀티모달 RAG
6. 잘린 청크의 맥락 소실1,000자 단위로 잘린 청크는 "어느 장비, 어느 절차의 일부인지" 정보를 잃음Contextual Retrieval계층 검색

💡 핵심 관점: 검색 지표가 만점이어도 "답변 품질"과 "질문의 복잡도"라는 두 축은 별개의 싸움입니다. 이번 파트의 기술들은 모두 이 표의 어딘가를 겨냥합니다.

💰 비용 어림 계산

전체 515K 청크: 청크당 입력 수백~1천 토큰 가정 시 수억 토큰 규모 — gpt-4o-mini급 API로도 수십 달러 수준이지만, 호출 수 자체가 부담.

현실적 전략: CCIE(103건) + 장비 매뉴얼(579건) 문서의 청크부터 적용. RFC 11,449건은 문서 구조가 정형적이라 우선순위가 낮고, 잘린 맥락 문제가 실제로 아픈 곳은 매뉴얼·교재입니다.

🏢 Microsoft GraphRAG 개요

Microsoft가 2024년 공개한 대표 구현체. LLM 자동 추출로 그래프를 만들고, 커뮤니티 단위 요약으로 "이 코퍼스 전체의 주제는?" 같은 글로벌 질문(Global Search)과 특정 엔티티 중심의 로컬 질문(Local Search)을 모두 지원하는 것이 특징입니다.

Multi-Query & RAG-Fusion 난이도 하기대효과 ★★

사용자의 질문 한 줄은 "의도의 한 단면"일 뿐 — 여러 관점으로 다시 묻고, 결과를 합치면 빠뜨림이 줄어듭니다.

⚙️ 동작 원리

① 재작성 — LLM이 "VLAN 트렁크 설정법"을 3~5개 변형으로: "트렁크 포트 구성 명령어", "802.1Q tagged port 설정", "switchport mode trunk 사용법"...
② 병렬 검색 — 변형 쿼리 각각으로 동시에 검색 (서로 다른 문서 집합이 걸려 올라옴)
③ RRF 결합 — 여러 결과 목록을 Reciprocal Rank Fusion으로 합산 → 여러 관점에서 공통으로 상위인 문서가 1등 (= RAG-Fusion)

HyDE와의 차이: HyDE는 "가짜 정답 문서" 1개를 만들어 그것으로 검색, Multi-Query는 "질문 자체"를 여러 개로 늘립니다. 서로 배타적이지 않아 함께 쓸 수 있습니다.

🛠️ 이 프로젝트에 적용하면

  • 위치: retriever/query.py — HyDE가 이미 있는 쿼리 변환 모듈에 multi_query() 함수 추가
  • 재사용: 결합 단계는 retriever/hybrid.py의 기존 RRF 코드를 그대로 호출 — 새 알고리즘 구현 불필요
  • 재작성 LLM: 짧은 작업이라 EXAONE 1.2B 로컬로 충분
  • 기대 효과: 표현이 다양한 한국어 질문의 recall 향상, 특히 동의어가 많은 장비 명령어 질문에 유리
  • 비용: 검색 횟수 ×N → 응답 시간 증가. 변형 3개 + 병렬 실행으로 억제

💡 기존 인프라(쿼리 변환 + RRF)를 조립만 하면 되는, 가장 "가성비 좋은" 기법 중 하나

질문 분해 (Query Decomposition) 난이도 중기대효과 ★★

Multi-Query가 "같은 질문을 여러 말투로"라면, 분해는 "한 질문을 여러 개의 작은 질문으로 쪼개는 것"입니다.

⚙️ 동작 원리 — 비교 질문 시연

질문: "다산과 유비쿼스 장비의 VLAN 설정 방법 차이는?"

① 분해 — LLM이 하위 질문 2개 생성:
Q1 "다산 장비의 VLAN 설정 방법은?"
Q2 "유비쿼스 장비의 VLAN 설정 방법은?"
② 개별 검색 — Q1은 다산 매뉴얼 청크, Q2는 유비쿼스 매뉴얼 청크가 각각 정확히 hit
③ 종합 — 두 검색 결과를 함께 LLM에 주고 "차이를 비교 정리"하도록 최종 답변 생성

통째로 검색하면 두 벤더 문서가 섞인 어중간한 결과가 나오지만, 쪼개면 각 하위 질문이 단순 검색으로 풀리는 수준까지 내려갑니다. 시험에서 큰 문제를 소문항으로 나눠 푸는 것과 같습니다.

🛠️ 이 프로젝트에 적용하면

  • 위치: retriever/query.py에 decompose() 추가 + retriever/rag.py에 "하위 질문별 검색 → 컨텍스트 병합" 루프
  • 분기 조건: 모든 질문을 분해하면 낭비 — "vs", "차이", "비교", 복수 엔티티 감지 시에만 작동(추후 Agentic 라우터로 일반화)
  • 메타데이터 시너지: Q1엔 doc_type=manual + 다산 필터, Q2엔 유비쿼스 필터를 자동 적용 가능 — Phase 2 필터 인프라 재활용
  • 기대 효과: 한계 #2의 비교형 질문 직접 해결
  • 비용: LLM 호출 +1, 검색 ×하위 질문 수

임베딩 파인튜닝 난이도 상기대효과 ★★

범용 임베딩 모델은 "OSPF"와 "BGP"를 그냥 '네트워크 용어'로 뭉뚱그릴 수 있습니다. 우리 도메인의 미세한 구분을 가르치는 작업입니다.

⚙️ 동작 원리 — Contrastive 학습

학습 데이터 = (질문, 정답 문서, 오답 문서) 삼중쌍(triplet)
학습 목표 = 질문 벡터를 정답 문서 벡터에는 가깝게 당기고, 오답 문서 벡터에서는 멀게 밀어내기

비유: 신입 사서에게 "이 질문엔 이 책이 정답, 비슷해 보이는 저 책은 오답"을 반복 훈련시켜 우리 도서관 전용 감각을 만드는 것. 모델 구조는 그대로, 벡터 공간의 배치만 도메인에 맞게 미세 조정됩니다.

ColBERT / Late Interaction 난이도 상기대효과 ★★

바이 인코더(빠름·대략적)와 크로스 인코더(느림·정밀)의 딱 중간 지점을 차지하는 제3의 방식입니다.

⚙️ 동작 원리 — 토큰 단위 매칭 (MaxSim)

저장: 청크를 벡터 1개로 뭉치지 않고, 토큰마다 작은 벡터를 전부 보관 ("문서 전체 요약" 대신 "단어별 지문" 보관)
검색: 질문의 각 토큰이 문서 토큰들 중 가장 비슷한 것과의 유사도(MaxSim)를 찾고, 이를 모두 합산해 점수화
Late Interaction: 인코딩은 미리(빠름), 토큰끼리의 상호작용 계산만 검색 시점에(정밀) — 그래서 "늦은 상호작용"

비유: 바이 인코더가 "두 사람의 첫인상 비교"라면, ColBERT는 "이력서를 항목별로 맞대 보는 것" — 단어 하나하나가 매칭되어 show ip ospf 같은 정확한 표현에 강합니다.

  • 옵션 A — 리랭커 대체: bge-reranker(크로스 인코더, 청크당 추론 필요)를 ColBERT로 바꾸면 리랭킹 단계가 수 배 빨라질 수 있음
  • 옵션 B — 1차 검색 보완: hybrid 검색의 제3 축으로 추가 후 RRF 결합

Parent-Document / 계층 검색 난이도 하기대효과 ★★

청킹의 딜레마 — 검색은 작은 청크가 유리하고, 답변 생성은 큰 맥락이 유리합니다. 둘을 분리하면 양쪽을 다 가질 수 있습니다.

⚙️ 동작 원리 — "작게 찾고, 크게 읽기"

① 인덱싱: 작은 자식 청크로 임베딩하되, 각 청크에 부모(상위 섹션/문서) ID를 기록
② 검색: 작은 청크로 정밀하게 매칭 (작을수록 주제가 단일해서 벡터가 또렷함)
③ 컨텍스트 제공: LLM에게는 hit한 청크가 아니라 그 부모 섹션 전체를 전달 — 절차의 앞뒤 단계가 함께 보임

비유: 색인(인덱스)으로는 한 줄짜리 키워드로 페이지를 찾고, 실제로 읽을 때는 그 장(章) 전체를 펼치는 것. "설정 절차 3단계만 잘려 오는" 문제가 사라집니다.

🛠️ 이 프로젝트에 적용하면 — 거의 공짜

  • 이미 있는 것: 구조 인식 청킹이 헤더 계층(#/##/###) 메타데이터를 청크마다 보존 중 — "부모 섹션"이 이미 식별 가능
  • 구현: retriever/rag.py의 컨텍스트 조립 단계에서, hit 청크의 (파일, 상위 헤더)로 같은 섹션 청크들을 store/에서 모아 병합
  • 일반화 관점: Phase 6의 "HyDE 인접 청크 확장"이 ±1개 이웃이라면, 이 기법은 "섹션 단위 이웃"으로 일반화한 것
  • 주의: 부모가 너무 크면 컨텍스트 윈도우(로컬 LLM 4096 토큰) 초과 — 섹션 길이 상한 필요
  • 판정: 재인덱싱 불필요, 검색 단계 무변경 → 저비용 고효율

Self-RAG ⑴ 동작 원리 난이도 중~상기대효과 ★★★

기존 RAG는 "무조건 검색 → 무조건 그 문서로 답변"하는 고정 라인 — Self-RAG는 매 단계마다 모델이 스스로 판단합니다.

🔎

→
📌
3. 답이 근거에 충실한가? [ISSUP] 토큰
생성한 문장이 문서에 의해

🏆
4. 어느 답이 유용한가? [ISUSE] 토큰
후보 답변들을 점수화해

🪞 비유: 답안을 내기 전에 스스로 채점하는 학생

보통 학생(기존 RAG)은 자료를 받으면 그대로 베껴 씁니다. Self-RAG는 "이 자료가 문제랑 맞나?" → "내 답이 자료에 실제로 있나?"를 혼잣말로 확인한 뒤 제출합니다. reflection(성찰) 토큰이 바로 그 혼잣말입니다.

📄 원 논문의 방식 vs 실전 경량화

원 논문(2023)은 reflection 토큰을 출력하도록 전용 학습한 모델을 사용합니다. 실무에서는 학습 없이 일반 LLM에게 "관련 있나? 근거 있나?"를 프롬프트로 묻는 경량 버전이 널리 쓰입니다 — 다음 슬라이드에서 이 방식으로 적용합니다.

🛠️ retriever/rag.py 개조 설계

CRAG (Corrective RAG) 난이도 중기대효과 ★★

Self-RAG가 "버릴 것을 거른다"면, CRAG는 한 걸음 더 — 검색이 실패했다고 판단되면 행동을 바꿔 다시 시도합니다.

⚙️ 동작 원리 — 평가기의 3분류

평가기(Retrieval Evaluator)가 검색 결과 묶음을 채점해 3등급으로 분류
Correct 충분히 정확 → 청크에서 핵심만 추려(refinement) 답변 생성
Incorrect 부정확 → 쿼리를 재작성해 재검색하거나 외부 검색(웹 등)으로 폴백
Ambiguous 애매 → 두 전략을 모두 수행해 결과 결합
Self-RAGCRAG
판정 단위청크·문장 개별검색 결과 묶음
실패 시 행동버리고 표시재검색·폴백
구현 형태전용 학습(원본)경량 평가기로 가능

🛠️ 이 프로젝트에 적용하면

  • 위치: retriever/rag.py에 평가→분기 루프 추가 (Self-RAG 게이트 ①을 묶음 단위로 확장하면 평가기가 됨)
  • 재검색 전략이 풍부한 게 강점: Incorrect 판정 시 ① 쿼리 재작성(HyDE/Multi-Query 재사용) ② 검색 모드 전환(hybrid → ontology) ③ 메타필터 완화 — 폐쇄망이라 웹 폴백 대신 모드 전환이 우리식 폴백
  • 루프 상한: 무한 재검색 방지 — 최대 2회 재시도 후 "찾지 못함" 반환
  • 기대 효과: 첫 검색이 빗나가는 드문 케이스(현재 MRR 0.893의 나머지)를 자동 회복

Agentic RAG ⑴ 동작 원리 난이도 상기대효과 ★★★

지금까지의 기법이 "파이프라인 개량"이라면, Agentic RAG는 파이프라인 자체를 LLM이 상황에 맞게 조립하는 패러다임 전환입니다.

⚙️ 핵심 구조 — 도구를 든 사서

LLM 에이전트에게 검색 방법들을 "도구(tool)"로 등록해 주면, 에이전트가 질문을 읽고 어떤 도구를 어떤 순서로 쓸지 스스로 결정합니다. 필요하면 여러 번 검색하고, 중간 결과를 보고 다음 행동을 바꿉니다.

🧰 도구 예시: 벡터 검색 / 하이브리드 검색 / 온톨로지 검색 / 메타데이터 필터 검색 / 질문 분해기
단순 질문 → 벡터 검색 1회로 끝
비교 질문 → 분해 후 필터 검색 2회 → 종합
개념-실무 연결 질문 → 온톨로지 검색 → 부족하면 hybrid 추가 검색

🔁 ReAct 패턴 — 에이전트의 사고 루프

Reasoning(추론) + Action(행동)의 반복:

Thought "이건 두 벤더 비교 질문이군. 나눠서 검색하자"
Action search(query="다산 VLAN", filter=manual)
Observation 다산 결과 확보. 유비쿼스가 아직 없다
Thought → Action → ... 충분해질 때까지 반복 후 최종 답변

비유: 사서가 "이 질문은 백과사전부터, 저 질문은 카탈로그부터" 하고 찾는 전략 자체를 머릿속으로 말하면서 움직이는 모습

⚠️ 강력하지만 비용도 큼 — 매 루프가 LLM 호출이라 지연·비용·예측 불가능성이 함께 옵니다. 그래서 로드맵의 후반부에 배치합니다.

PART 3 — ④ 에이전트화

Agentic RAG ⑵ 이 프로젝트에 적용하면 — 도구는 이미 4개 있다

vector / bm25 / hybrid / ontology — 기존 4개 검색 모드가 그대로 에이전트의 도구 세트입니다. 만들 것은 "고르는 두뇌"뿐.

🛠️ 라우터 에이전트 설계안

1단계 — 정적 라우터(쉬움): LLM 1회 호출로 질문을 분류(단순/비교/개념연결/명령어)하고 모드·필터를 선택만 하는 라우터. 루프 없음 → 비용 +1회로 제한적 효과 확보
2단계 — ReAct 루프(어려움): retriever/의 각 모드를 함수 도구로 등록, 관찰-재검색 루프 허용(상한 3회). CRAG의 재검색 분기를 일반화한 형태
CLI 인터페이스: mdrag ask "..." --agentic 플래그 신설 — 기존 ask 경로는 그대로 보존해 회귀 안전성 확보
API: POST /api/v1/ask에 agentic: true 옵션 추가

🎬 시나리오: mdrag ask --agentic

"유비쿼스 장비에서 OSPF 영역을 나누는 표준 근거와 설정 명령을 알려줘"

분류: 개념(표준)+실무(명령) 복합 → ontology 모드 선택
검색: rfc:2328 카드 hit + 유비쿼스 매뉴얼 청크 주입
관찰: 명령 예시 부족 → hybrid + manual 필터로 추가 검색
종합: 표준 근거(RFC) + CLI 명령을 묶어 답변

⚖️ 효과 / 주의

  • 효과: 사용자가 모드를 몰라도 최적 검색 — UX 단순화 + 복합 질문 해결
  • 주의: 1.2B 로컬 모델로는 라우팅 판단이 불안정할 수 있어 1단계는 로컬, 2단계는 클라우드 LLM 권장

PART 3 — ⑤ 평가 · 운영

RAGAS & LLM-as-Judge 평가 난이도 하~중기대효과 ★★★

"측정이 곧 개선" — 검색은 Hit@5/MRR로 측정해 왔지만, 생성(답변)은 아직 시험을 본 적이 없습니다.

⚙️ 동작 원리 — 4대 지표

RAGAS는 (질문, 검색 컨텍스트, 답변)을 LLM 심판(LLM-as-Judge)에게 채점시키는 프레임워크입니다:

  • Faithfulness (충실성) — 답변의 각 주장이 컨텍스트에 근거하는가? 낮으면 = 환각
  • Answer Relevancy (답변 관련성) — 답변이 질문에 실제로 대답하는가? 동문서답 감지
  • Context Precision (정밀도) — 가져온 컨텍스트 중 쓸모 있는 비율은? 잡음 측정
  • Context Recall (재현율) — 정답에 필요한 정보를 빠짐없이 가져왔는가?

비유: 검색 지표가 "자료를 잘 찾아왔나"의 채점이라면, RAGAS는 "그 자료로 쓴 답안"까지 채점하는 논술 시험관입니다.

🛠️ 이 프로젝트에 적용하면

  • 위치: scripts/validate_rag.py를 확장 — 현재 100건 검증을 "검색 채점"에서 "검색 + 생성 채점" 2부 구성으로
  • 데이터 보강: 100건에 모범 답안(ground truth answer) 필드 추가 필요 (recall 계산용)
  • 심판 모델: 채점 일관성이 중요하므로 1.2B 로컬보다 클라우드 LLM 권장 — 100건 × 4지표는 소액
  • 회귀 테스트 통합: "변경 후 faithfulness가 떨어지면 머지 금지" 같은 품질 게이트를 CI에 연결
  • 판정: 다른 모든 기술의 효과를 측정할 "저울"이므로 최우선 도입 — 저울 없이 개선 없음

PART 3 — ⑤ 평가 · 운영

시맨틱 캐싱 & 성능 최적화 난이도 하기대효과 ★★

같은 질문이 매번 1.9초의 전체 파이프라인을 다시 탈 이유가 없습니다 — "의미가 같은 질문"까지 캐시로 잡는 것이 핵심입니다.

⚙️ 동작 원리

① 저장: (질문 임베딩, 검색 결과, 최종 답변)을 캐시에 보관
② 판정: 새 질문이 오면 임베딩을 만들어 캐시 속 질문 벡터들과 유사도 비교 — 문자열이 달라도 의미가 같으면 hit ("OSPF 영역이란?" ≈ "OSPF area가 뭐야?")
③ 반환: 임계값(예: 유사도 0.95↑) 이상이면 저장된 답을 즉시 반환 — 검색·리랭킹·LLM 전부 생략 → 수십 ms

비유: 자주 묻는 질문(FAQ) 게시판을 "표현이 달라도 알아보는" 똑똑한 FAQ로 만든 것. 임베딩 계산(이미 로컬, 빠름)만으로 판정하므로 miss여도 손해가 거의 없습니다.

🛠️ 이 프로젝트에 적용하면

  • 위치: api/ ask 엔드포인트 앞단 + retriever/rag.py 입구에 캐시 레이어. 저장소는 초기엔 로컬 파일/SQLite로 충분
  • 무효화 규칙: ingest로 문서가 갱신되면 캐시 비우기 — 오래된 답 방지
  • 주의: 임계값이 낮으면 "비슷하지만 다른 질문"에 엉뚱한 답을 재사용하는 사고 — 보수적(높게) 시작
  • 함께 갈 최적화: 임베딩 모델 ONNX 변환/양자화로 추론 가속, 리랭커 배치 크기 튜닝, BM25 인덱스 메모리 상주 확인
  • 기대 효과: 반복 질문 비중이 높은 사내 환경일수록 체감 큼 — 한계 #4 직격

PART 3 — ⑤ 평가 · 운영

멀티모달 RAG 난이도 상기대효과 ★★

장비 매뉴얼의 절반은 토폴로지 그림과 설정 표입니다 — 텍스트만 인덱싱하면 그 절반이 검색 사각지대가 됩니다.

⚙️ 동작 원리 — 두 가지 접근

접근 A — 캡셔닝(현실적): 비전 LLM이 그림을 보고 텍스트 설명을 생성("V8500 2대를 링으로 연결한 GPON 구성도...") → 그 텍스트를 일반 청크처럼 인덱싱. 기존 파이프라인 무변경
접근 B — 멀티모달 임베딩(정통): CLIP 계열 모델로 이미지와 텍스트를 같은 벡터 공간에 임베딩 → 텍스트 질문으로 이미지를 직접 검색

비유: A는 그림마다 "그림 설명 카드"를 써서 색인에 끼워 넣기, B는 색인 자체가 그림과 글을 같은 언어로 이해하게 만들기. A가 훨씬 싸고, 표(테이블)는 Markdown 변환으로 함께 해결 가능합니다.

🛠️ 이 프로젝트에 적용하면

  • 대상 선별: 다산·유비쿼스 매뉴얼 579건의 원본에서 이미지 추출 — RFC는 텍스트 위주라 제외
  • 접근 A 권장: ingest/에 이미지 → 캡션 단계 추가, 캡션 청크에 content_type=image_caption + 원본 이미지 경로 메타데이터 부여 → 답변 시 "그림 N 참조" 링크 제공
  • 제약: 캡셔닝엔 비전 모델 필요 — 폐쇄망이면 로컬 비전 모델(수 GB) 도입 검토 과제
  • 기대 효과: "이 구성도처럼 연결하려면?" 류 질문 대응 — 한계 #5 해소
  • 판정: 가치는 분명하나 신규 모델 도입 부담 → 로드맵 최후반

🧭 단계 선정 이유

  • 1단계가 먼저인 이유: RAGAS 없이는 2~4단계의 효과를 증명할 수 없고, Contextual Retrieval은 모든 검색 기법의 기반인 인덱스 자체를 좋게 만듭니다.
  • 2단계가 다음인 이유: 셋 다 이미 가진 코드(RRF·임베딩·온톨로지 스키마)의 재조립 — 새 위험 없이 체감 개선.
  • 3단계를 미루는 이유: 검증·에이전트는 LLM 호출이 늘어 비용과 지연을 동반 — 측정 체계(1단계)가 있어야 트레이드오프를 관리할 수 있습니다.
  • 4단계가 마지막인 이유: 재인덱싱 전면 재작업(파인튜닝)과 신규 모델 도입(비전)은 되돌리기 가장 비싼 결정입니다.

SERIES FINALE

시리즈 마무리 — Part 1 · 2 · 3 핵심 요약

세 파트를 관통하는 결론은 하나입니다 — RAG는 단일 기술이 아니라, 측정 위에서 조합하는 시스템입니다.

PART 1 — 개념

RAG = 오픈북 시험. LLM의 환각·시점 한계·사내 문서 부재를 "검색해서 근거를 쥐여 주는" 구조로 해결한다. 책(인덱스)의 품질이 답의 품질을 결정한다.

PART 2 — 구조

약점은 조합으로 보완한다. 벡터+BM25 하이브리드, 리랭킹, HyDE, 온톨로지 카드 69장의 조합이 12,131건 코퍼스에서 Hit@5 60%→100%를 만들었다.

PART 3 — 진화

다음 전선은 생성 품질과 복합 질문. 측정(RAGAS)과 인덱스 보강(Contextual)을 깔고, 그래프·자기 검증·에이전트로 단계적으로 확장한다.

🎯 마지막 한 문장

유행하는 기법을 좇는 것이 아니라, 우리 시스템의 한계를 진단하고 → 그 한계를 겨냥한 기술을 고르고 → 같은 저울(검증 데이터셋)로 전후를 측정하는 것 — 이 루프를 돌릴 수 있는 팀만이 RAG를 "계속 좋아지는 시스템"으로 운영할 수 있습니다.
