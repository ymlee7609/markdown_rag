PART 1 — 기본 개념

왜 RAG가 필요한가?

LLM(대규모 언어 모델)은 똑똑하지만, 혼자서는 해결하지 못하는 3가지 근본적 한계가 있습니다.

🌫️ 환각 (Hallucination)

모르는 내용도 그럴듯하게 지어냅니다. "RFC 2328의 3.2절 내용은?" 같은 질문에 존재하지 않는 내용을 자신 있게 답할 수 있습니다.

📅 지식의 시점 한계

학습 데이터 마감 시점 이후의 정보를 모릅니다. 어제 업데이트된 장비 매뉴얼이나 신규 정책은 답할 수 없습니다.

🔒 사내 문서 접근 불가

회사 내부 매뉴얼, 기술 문서, 위키는 학습된 적이 없습니다. CCIE 교재나 다산/유비쿼스 장비 설정법은 모델 안에 없습니다.

💡 해결책: RAG (Retrieval-Augmented Generation, 검색 증강 생성)

질문이 들어오면 ① 내 문서 저장소에서 관련 내용을 먼저 검색(Retrieval)하고, 찾아낸 근거 문서를 ② LLM에게 함께 전달하여 답변을 생성(Generation)하게 하는 방식입니다. 즉, "오픈북 시험"을 치르게 하는 것 — 모델이 외운 지식이 아니라 실제 문서를 근거로 답하므로 환각이 줄고, 최신·사내 문서도 활용할 수 있습니다.

RAG의 기본 구조 — 3단계 파이프라인

모든 RAG 시스템은 본질적으로 「인덱싱 → 검색 → 생성」 세 단계로 구성됩니다.

📚
1. 인덱싱 (Indexing) 문서를 작은 조각(청크)으로 나누고, 각 조각을 숫자 벡터(임베딩)로 변환해 벡터 DB에 저장.
"검색 가능한 도서관 만들기"
→
🔍
2. 검색 (Retrieval) 사용자 질문도 벡터로 변환한 뒤, 의미가 가장 가까운 청크 Top-K개를 찾아냄.
"질문과 관련된 페이지 찾기"
→
✍️
3. 생성 (Generation) 검색된 청크들을 "참고 자료"로 프롬프트에 넣고, LLM이 근거 기반 답변을 작성.
"자료 보고 답안 쓰기"

⏱️ 사전 작업 vs 실시간

인덱싱은 문서가 추가/변경될 때 한 번만 수행하는 사전 작업이고, 검색 + 생성은 질문이 들어올 때마다 실행되는 실시간 작업입니다. 그래서 인덱싱 품질(청킹 전략)이 전체 시스템 품질의 절반을 결정합니다.

🆚 파인튜닝과의 차이

파인튜닝은 모델 자체를 재학습시키는 방식(비싸고 느림, 갱신 어려움), RAG는 모델은 그대로 두고 지식만 외부 DB로 분리하는 방식입니다. 문서가 자주 바뀌는 환경에선 RAG가 압도적으로 유리합니다.

핵심 용어 사전 — 이것만 알면 RAG 대화 가능

RAG 문서나 코드를 읽을 때 반복 등장하는 7가지 필수 개념입니다.

청킹 (Chunking)

긴 문서를 검색 가능한 작은 조각으로 나누는 것. 너무 크면 잡음이 섞이고, 너무 작으면 맥락이 끊깁니다. (본 프로젝트: 최대 1,000자 + 중첩 100자)

임베딩 (Embedding)

텍스트를 의미를 담은 숫자 배열(벡터)로 변환. "인증 방식"과 "Authentication"처럼 표현이 달라도 의미가 비슷하면 벡터도 가까워집니다.

벡터 DB (Vector Database)

수십만 개 벡터 중에서 질문 벡터와 가장 가까운 것을 빠르게 찾아주는 전용 데이터베이스. (본 프로젝트: ChromaDB)

유사도 검색 (Similarity Search)

벡터 간 거리(코사인 유사도 등)를 계산해 "의미가 가까운" 문서를 찾는 것. 키워드가 일치하지 않아도 의미로 검색됩니다.

Top-K

검색 결과 중 상위 K개만 LLM에게 전달. K가 크면 정보가 풍부하지만 잡음과 비용이 늘어납니다. (본 프로젝트: 기본 5)

키워드 검색 (BM25)

전통적 검색엔진 방식. 정확한 용어 매칭(예: "RFC 2328", 명령어 이름)에 강해서 벡터 검색의 약점을 보완합니다.

컨텍스트 윈도우 (Context Window)

LLM이 한 번에 읽을 수 있는 텍스트 분량 제한. 검색된 청크 + 질문 + 답변이 이 안에 들어가야 하므로 "무엇을 넣을지" 선별이 중요합니다.

Hit@K / MRR (평가 지표)

Hit@K: 정답 문서가 상위 K개 안에 있는 비율. MRR: 정답이 몇 등으로 검색됐는지의 평균(1등이면 1.0). 검색 품질을 숫자로 측정하는 표준 지표입니다.

② 하이브리드 검색 — 벡터 + 키워드의 결합 Phase 3

벡터 검색과 BM25는 서로의 약점을 정확히 보완합니다. 둘을 합치는 것이 현대 RAG의 표준입니다.

🧭 벡터 검색 (의미 기반)

  • 강점: 표현이 달라도 의미가 같으면 찾음 — "인증 방식" ↔ "Authentication mechanism"
  • 약점: 고유명사·정확한 코드에 약함 — "RFC 2328", show ip ospf 같은 정확 매칭을 놓침

🔑 BM25 키워드 검색 (단어 기반)

  • 강점: 정확한 용어·명령어·번호 매칭에 강함 — 기술 문서 검색의 필수 요소
  • 약점: 동의어·번역 표현을 못 찾음. 한국어는 조사 분리가 필요 → kiwipiepy 형태소 분석으로 해결

🔀 RRF (Reciprocal Rank Fusion) — 두 결과를 합치는 방법

두 검색의 점수 체계가 달라 단순 합산이 불가능하므로, 순위(rank)만 사용해 결합합니다: 각 결과의 점수를 1 / (k + 순위)로 환산해 더하면, 양쪽 모두에서 상위권인 문서가 자연스럽게 1등이 됩니다. 벡터 가중치 alpha=0.7로 의미 검색을 약간 우대 — mdrag search "인증 방식" --search-mode hybrid

③ 검색 정확도 끌어올리기 — 리랭킹 & HyDE

1차 검색 결과를 한 번 더 다듬는 두 가지 고급 기법이 적용되어 있습니다.

Phase 4 크로스 인코더 리랭킹

2단계 검색 전략 — 빠른 검색기로 후보 20개를 넓게 가져온 뒤(initial_top_k=20), 더 정밀하지만 느린 모델로 재채점하여 최종 Top 5를 선별합니다.

임베딩(바이 인코더): 질문과 문서를 따로 벡터화 → 빠르지만 대략적
크로스 인코더: 질문+문서를 한 쌍으로 함께 읽고 관련도 채점 → 느리지만 정밀
모델: BAAI/bge-reranker-v2-m3 (다국어 지원)

"서류 전형(임베딩)으로 20명 추리고, 면접(리랭커)으로 5명 선발"하는 구조

Phase 6 HyDE (가상 문서 임베딩)

질문과 문서는 생김새가 다르다는 문제를 해결합니다. "OSPF가 뭐야?"(질문체)와 "OSPF는 링크 상태 라우팅 프로토콜로..."(설명체)는 벡터 공간에서 거리가 있습니다.

① 질문을 받으면 LLM이 가상의 정답 문서를 먼저 작성
② 질문 대신 그 가상 문서를 임베딩하여 검색
③ "문서 ↔ 문서" 비교가 되어 유사도 매칭 정확도 향상

+ 검색된 청크의 인접 청크를 함께 컨텍스트에 추가해 잘린 맥락을 복원

④ 온톨로지 증강 검색 — 이 프로젝트의 시그니처 Phase 7

"OSPF area 설정"이라는 질문 하나가 표준(RFC) · 이론(CCIE) · 실무(장비 매뉴얼)에 흩어져 있다면? — 지식 카드로 연결합니다.

🃏 온톨로지 카드 = 사람이 만든 지식 지도 (69장)

프로토콜·개념·RFC·장비별로 핵심 엔티티를 정의한 카드를 보조 코퍼스(input_ontology/)로 운영합니다. 각 카드는 YAML frontmatter로 실제 문서와의 연결 고리를 가집니다.

id: proto:ospf # 엔티티 8종 / 관계 14종
name_ko: 개방형 최단 경로 우선
defined_by: [rfc:2328] # → 표준
taught_in: [CCIE_Vol1/04_...md] # → 이론
documented_in: [다산_L3] # → 실무 CLI
keywords_ko: [영역, 인접관계, 헬로]

📂 카드 구성 (총 69장)

  • protocols (18) — OSPF, BGP, STP, VLAN, DHCP, GPON ...
  • concepts (14) — ospf-area, bgp-as-path, vlan-trunk ...
  • rfcs (13) — 2328, 4271, 8200, 5905 ...
  • standards (3) — IEEE 802.1D/Q, ITU-T G.984
  • features (7) — mac-address-table, port-mirroring ...
  • vendors (2) + devices (8) — 다산, 유비쿼스 장비

+ 영문/한글 별칭 사전(alias dictionary)으로 "스패닝트리"="STP"="Spanning Tree" 통합

앞으로 적용할 수 있는 기술 ① — 검색 품질 고도화

현재 구조에서 자연스럽게 이어지는 다음 단계의 검색 기법들입니다.

우선순위 높음 GraphRAG (지식 그래프 RAG)

현재의 온톨로지 카드(69장, 수동)를 완전한 지식 그래프로 확장. LLM이 문서에서 엔티티·관계를 자동 추출해 그래프를 구축하고, 다중 홉 질문 ("RFC 2328을 구현한 장비 중 GPON을 지원하는 것은?")에 그래프 탐색으로 답합니다. 이미 entity/relation 스키마가 있어 전환 비용이 낮습니다.

우선순위 높음 Contextual Retrieval (맥락 보강 청킹)

인덱싱 시 각 청크 앞에 "이 청크는 어떤 문서의 어떤 맥락인지" 설명을 LLM으로 생성해 붙인 뒤 임베딩하는 기법(Anthropic 발표). 잘린 청크의 맥락 소실 문제를 근본적으로 해결하며, 검색 실패율을 크게 줄이는 것으로 알려져 있습니다.

중기 쿼리 변환 — Multi-Query & 분해

HyDE에서 한 걸음 더: 하나의 질문을 여러 관점의 쿼리로 재작성(Multi-Query)하거나 복합 질문을 하위 질문으로 분해(Decomposition)해 각각 검색 후 결합(RAG-Fusion). "다산과 유비쿼스의 VLAN 설정 차이"같은 비교 질문에 효과적입니다.

중기 임베딩 파인튜닝 & ColBERT

네트워크 도메인 질문-문서 쌍으로 임베딩 모델을 파인튜닝하면 전문 용어 검색력이 향상됩니다. 또한 토큰 단위로 정밀 매칭하는 ColBERT(late interaction)는 바이 인코더의 속도와 크로스 인코더의 정밀도 사이의 균형점을 제공합니다.

앞으로 적용할 수 있는 기술 ② — 자기 검증 & 에이전트화

검색을 넘어, 시스템이 스스로 판단하고 행동하는 차세대 RAG 패러다임입니다.

패러다임 Self-RAG / CRAG (자기 교정 RAG)

검색 결과를 LLM이 스스로 평가: "이 문서가 질문과 관련 있나? 답변이 문서에 근거하나?" 관련성이 낮으면 재검색하거나 쿼리를 수정(Corrective RAG)합니다. 잘못된 문서로 잘못된 답을 만드는 RAG 최대의 리스크를 구조적으로 차단합니다.

패러다임 Agentic RAG (에이전트형 RAG)

고정 파이프라인 대신 LLM 에이전트가 검색 전략을 동적으로 선택: 단순 질문은 벡터 검색만, 비교 질문은 분해 후 다중 검색, 설정 질문은 온톨로지 모드 — 질문 유형에 따라 도구를 골라 쓰고, 필요시 여러 번 검색을 반복합니다.

운영 RAGAS 기반 자동 평가 + 답변 품질 측정

현재는 검색 품질(Hit@5, MRR)만 측정 — 다음 단계는 생성 품질 평가입니다. RAGAS 같은 프레임워크로 충실성(faithfulness)·답변 관련성·컨텍스트 정밀도를 자동 채점하고, LLM-as-Judge로 회귀 테스트를 답변 차원까지 확장합니다.

운영 시맨틱 캐싱 & 멀티모달 확장

유사 질문의 답변을 캐싱해 응답 시간(현재 ~1.9초)을 단축하고, 장비 매뉴얼의 네트워크 토폴로지 그림·표를 멀티모달 임베딩으로 인덱싱하면 "이 그림의 구성에서..." 같은 질문도 처리할 수 있습니다.
